## Резюме для руководства (Executive Summary)

Проект "Pages" в его текущем состоянии представляет собой **монолитное Django-приложение (MPA)**, где фронтенд реализован с помощью серверных шаблонов и нативного JavaScript. Эта архитектура проста, но **не отвечает современным требованиям** к интерактивным веб-приложениям, что приводит к проблемам с производительностью, качеством кода и скоростью разработки.

**Ключевая проблема:** Отсутствие современной фронтенд-архитектуры. Код на JavaScript хаотичен, не тестируется, состояние управляется небезопасно, а пользовательский опыт страдает от постоянных перезагрузок страниц.

**Главная рекомендация:** Начать **постепенный переход** от MPA к **SPA (Single-Page Application)** с использованием современного фреймворка (например, React или Vue). Это стратегическое вложение, которое кардинально повысит качество, производительность и поддерживаемость продукта.

## 1. Обзор архитектуры

*   **Текущая архитектура:** MPA (Multi-Page Application) на базе Django. Рендеринг происходит на сервере. Интерактивность добавляется через изолированные Vanilla JS скрипты.
*   **Сильные стороны:** Быстрый старт, простота для малоинтерактивных страниц, хорошая индексация поисковиками.
*   **Слабые стороны:**
    *   **Низкая производительность UX:** Полная перезагрузка страницы при каждом действии.
    *   **Плохая масштабируемость:** Сложно добавлять новую интерактивность без дублирования кода и создания "спагетти-кода".
    *   **Ненадежность:** Клиентский код хрупкий и тесно связан с HTML-структурой.
*   **Рекомендации по рефакторингу:**
    *   **Приоритет 1 (Стратегический):** Принять решение о переходе на SPA. Рекомендуемый подход — **"Strangler Fig Pattern"**. Начать с одной, наиболее сложной игры (например, "Craps"). Создать для нее компонент на React/Vue, который будет жить на существующей Django-странице и общаться с бэкендом через API. Постепенно "душить" старый фронтенд, заменяя страницу за страницей.
    *   **Приоритет 2 (Тактический):** При переходе на SPA использовать методологию **Feature-Sliced Design** для организации кода. Это обеспечит высокую модульность и упростит работу в команде.

## 2. Технологический стек и зависимости

*   **Ключевые технологии (Frontend):** Django Templates, CSS, Vanilla JavaScript. **Отсутствуют:** сборщики (Webpack/Vite), пакетные менеджеры (NPM/Yarn), JS-фреймворки.
*   **Бэкенд-зависимости:** `requirements.txt` содержит необычную смесь из `Django`, `Flask` и `FastAPI`. Это может указывать на неиспользуемый код или неудачные эксперименты. Также присутствуют `pygame` и `ttthemes`, что нетипично для веб-проекта.
*   **Рекомендации:**
    *   **Приоритет 1:** Создать **API-слой** на базе уже имеющегося `djangorestframework` для общения между новым SPA-фронтендом и бэкендом.
    *   **Приоритет 2:** Провести ревизию `requirements.txt`. Удалить неиспользуемые или избыточные зависимости (например, если Flask/FastAPI не используются), чтобы уменьшить потенциальные уязвимости и упростить окружение.
